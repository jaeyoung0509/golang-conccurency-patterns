# Go CSP vs Rust Tokio

Go and Rust both support highly concurrent systems, but they get there very differently.

This page is not about declaring a winner. It is about understanding the trade.

:::tip Quick takeaway
Go puts more concurrency machinery into the language and runtime: goroutines, channels, `select`, netpoll integration, and stackful execution. Rust plus Tokio puts more machinery into futures, executors, traits, and library-level composition.
:::

## The shortest comparison

| Question | Go | Rust + Tokio |
| --- | --- | --- |
| Unit of work | goroutine | future/task |
| Execution style | stackful goroutine | stackless state machine generated by `async` |
| Scheduler | built into runtime | executor in Tokio runtime |
| I/O integration | runtime netpoller | Tokio reactor/resource drivers |
| Coordination style | channels and `select` are first-class | channels, `select!`, and await-driven composition live in libraries/macros |
| Cancellation style | `context`, channel close, explicit ownership | drop, abort, cancellation tokens, `select!` patterns |

## How CSP shows up in Go

Go directly exposes CSP-shaped tools:

- `go` to launch concurrent processes,
- `chan T` as communication edges,
- `select` as choice between communication events.

That makes process composition feel native.

## How Tokio approaches the same space

Tokio is an async runtime for Rust. The important mental model is:

- `async fn` compiles into a future state machine,
- futures do nothing until polled by an executor,
- Tokio provides a scheduler, timer driver, and I/O driver so those tasks can make progress.

This means Tokio concurrency is usually described in terms of:

- tasks,
- `.await` yield points,
- executors,
- async I/O resources,
- `select!`,
- channels such as `mpsc`, `oneshot`, and `watch`.

## Where the biggest implementation difference comes from

Go goroutines are stackful.

That means ordinary blocking-looking code can suspend and resume without the programmer turning each suspension point into an explicit future state machine.

Rust futures are stackless and cooperatively polled.

That gives Rust:

- stronger static control over lifetimes and ownership,
- no hidden stackful coroutine runtime model,
- very explicit suspension points at `.await`.

It also means Tokio code often requires more explicit structure to express the same workflow.

## Scheduling and fairness

Go's runtime scheduler can asynchronously preempt CPU-heavy goroutines and integrate netpoll wakeups directly into scheduling.

Tokio tasks are generally cooperative. A task makes progress when it is polled and yields at `.await` points or other cooperative boundaries.

That difference changes engineering style:

- Go can make direct-style code ergonomically cheap,
- Tokio makes suspension points more explicit and often more analyzable.

## Channels and request composition

Go's channel story is deeper in the language surface.

Rust plus Tokio still supports channel-based designs, but channels are library primitives rather than language primitives. As a result:

- Go code often reaches for channels earlier,
- Tokio code often mixes channels with mutexes, atomics, and ownership transfer through typed values,
- request coordination in Tokio may center on `join!`, `select!`, `mpsc`, `oneshot`, and task handles rather than CSP-flavored process networks alone.

## Cancellation

Cancellation is another good contrast.

In Go:

- `context.Context` is the dominant request-lifetime tool,
- channel close is often a lifecycle signal,
- goroutine shutdown is usually an application protocol question.

In Tokio:

- dropping a future or task handle matters,
- cancellation tokens or select-based cancellation are common,
- structured task composition is more explicit in the library layer.

## Tiny comparison sketch

Go version:

```go
for req := range requests {
	go func(req Request) {
		replies <- handle(req)
	}(req)
}
```

Tokio version:

```rust
while let Some(req) = requests.recv().await {
    let replies = replies.clone();
    tokio::spawn(async move {
        let res = handle(req).await;
        let _ = replies.send(res).await;
    });
}
```

The surface problem is similar. The control points differ: Go leans on goroutines and `select`, while Tokio makes async boundaries, task spawning, and channel ownership more explicit in the library layer.

## When Go feels better

Go often feels better when:

- you want direct-style network service code,
- you want channels and `select` to be a default composition tool,
- you want runtime-managed goroutine scheduling without building the mental model around poll-based futures.

## When Tokio feels better

Tokio often feels better when:

- ownership and lifetime constraints should be pushed into the type system,
- you want explicit async boundaries,
- you want the broader Rust ecosystem around zero-cost abstractions and tight control over allocation and layout.

## Failure pattern

Porting goroutine habits directly into Tokio usually means detaching work without a clear backpressure or cancellation handle:

```rust
for req in requests {
    tokio::spawn(async move {
        let _ = handle(req).await;
    });
}
```

The mistake is conceptually familiar to Go engineers too, but Go's CSP defaults often push you toward explicit coordination earlier. Tokio makes that coordination possible, but not implicit.

## Practical takeaway

Go and Tokio are not two skins on the same model.

They both support large concurrent systems, but they encode the complexity at different layers:

- Go: more in the language and runtime,
- Tokio: more in futures, executors, and library composition.

Understanding that difference helps you choose patterns more intentionally, and it sharpens your sense of what Go is really buying you.
